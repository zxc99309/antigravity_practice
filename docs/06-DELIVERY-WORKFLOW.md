# 06｜每週工作流、提交與 Review 規範

## 一個工作單的完整週期

1. **Issue**：寫背景、角色、輸入資料、業務定義、限制、驗收條件（AC）與非目標。
2. **Design Note**：畫 1 張流程圖，列 Schema、來源、去重/時間策略、失敗恢復與替代方案。
3. **Branch**：命名如 `training/p03-w11-watermark`；只針對一張工作單。
4. **Implement**：先寫可觀察的失敗案例/測試，再最小實作，不提前引入本 Phase 以外的框架。
5. **Verify**：執行 tests / SQL 對帳 / 新舊結果差異 / 安全檢查；將命令和輸出保留在 PR 描述。
6. **Review**：依工程、分析和資料品質三條視角檢查；不接受模糊的「AI 測過沒問題」。
7. **Demo**：學習者不用 AI 重演主要路徑，Reviewer 臨時改一個條件或注入小故障。
8. **Retrospective**：學習筆記、困難點、未決問題、下一週前置依賴。

## PR 描述必含

```markdown
## 業務需求與範圍
## 設計與不變條件
## 變更檔案清單
## 測試 / 對帳證據（命令、環境、結果）
## 故障演練與復原證據
## 資料與安全檢查
## 分析口徑與限制（如適用）
## NotRun / 未完成 / 後續工作
## 本人答辯（被問到什麼、如何驗證）
```

## 資料管線日常維運 SOP

- **每日**：確認 last successful run、資料新鮮度、row counts、品質警示、下游刷新時間與主要業務指標是否異常。
- **每週**：檢查失敗重試、資料退化、成本與效能、技術債、業務變更，更新 Data Contract。
- **事件中**：不要先重跑破壞性工作；確認缺失/重複範圍、影響表、批次與版本；凍結證據；制定安全復原與對帳計畫。
- **事件後**：用 [Incident 模板](templates/INCIDENT-REPORT.md) 紀錄根因、時間線、受影響範圍、恢復驗證和預防措施。

## 安全與文件品質

- 公開專案一律使用 synthetic data；不要提交 `.env`、token、連線密碼、真實薪資／客戶資料、log 內的識別資訊。
- 以官方文件為准，標註技術版本與 OS 差異，命令只適用於描述的環境。
- 每個 AC 必須在 PR 有明確證據；若未驗證請寫 `NotRun`，不可腦補。
- AI 不能自動 merge；Review 與是否合併由 Repository 維護者決定。
